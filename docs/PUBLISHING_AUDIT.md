## 🔴 BLOCKERS — guaranteed or near-certain rejection / cannot submit


### 2. [GOOGLE] Account-deletion route not discoverable as a URL (downgraded 2026-07-29)
- **Re-verified 2026-07-29 — the substance already exists.** The live privacy policy covers deletion: §8 states that on a deletion request the account data is *"fshihen menjëherë nga të gjitha bazat e të dhënave"* with a legal/financial retention carve-out; §9 lists the full data-subject rights under Ligji 124/2024; §14 gives `dpo@rtsh.al` as the route to exercise them. The original finding ("no web deletion resource exists") searched the **repo** rather than reading the published policy, and was wrong.
- **What is actually missing is labelling, not policy.** No section is titled *account deletion*, there is no anchor to link to, and a reviewer must assemble the answer from §8 + §9 + §14. The Data safety field expects a URL that lands on an unambiguous deletion route.
- **Fix (~10 min, RTSH web):** add a titled section with an `id` (e.g. `<h2 id="fshirja-e-llogarise">Fshirja e llogarisë dhe e të dhënave</h2>`) naming the app, both routes (in-app `Profili → Fshi llogarinë`, and email `dpo@rtsh.al` from the registered address *even after uninstalling*), what is deleted, and the timeframe. Paste `…/#fshirja-e-llogarise` into Play Console → App content → Data safety.
- **Evidence (in-app half, unchanged):** in-app deletion exists and is correct ([profile.tsx](src/app/(app)/(tabs)/profile.tsx) → `DELETE /users/me`, wipe only on confirmed 200).
- **Policy:** Play User Data policy (enforced since 2024-04-15): apps with in-app account creation must also provide a **web link** where users can request account + data deletion *without reinstalling the app*. The URL is a required field in the Data safety form — you cannot complete the form (and therefore cannot release) without it. Source: https://support.google.com/googleplay/android-developer/answer/13327111
- **Fix:** backend/web team hosts a deletion-request page (email-verified form is acceptable); enter it in Play Console → App content → Data safety. Apple doesn't mandate the web link, but the same page strengthens the 5.1.1(v) story.

### 3. [BOTH] No review-account strategy — login wall + email OTP + geo-blocked streams
- **Evidence:** registration requires an emailed OTP ([ARCHITECTURE.md → Auth flow §6]); all content sits behind login; channel/programme playback is geo-enforced at the CDN ([ARCHITECTURE.md → Real-time → Geo]). App Review (Apple) and the Play pre-launch report both run from **US IPs on fresh devices**.
- **Policy:** Apple 2.1 App Completeness (demo account required for gated apps; the #1 rejection cause); Play Console → App content → **App access** (test credentials mandatory for gated apps).
- **Fix (all three parts needed):**
  a. Pre-provisioned review accounts (skip OTP — a reviewer can't read your inbox) for both consoles.
  b. Backend: ensure the review account can actually play streams from US IPs (geo-allowlist for the review account, or non-geoblocked channels available), otherwise the app looks broken.
  c. Review notes explaining the service (Albanian public broadcaster), the geo model, and the parental-PIN demo steps.

### 4. [BOTH] Publisher identity & content rights not settled
- **Evidence:** `owner: 'anxheloo'` ([app.config.ts:161](app.config.ts#L161)) — a personal Expo account; bundle `al.rtsh.tani` carries the national broadcaster's brand.
- **Policy:** Apple 5.2.1/5.2.2 (apps must be submitted by the rights holder or with documented authorization — brand apps from unrelated personal accounts get rejected and risk the developer account); Play Impersonation policy (same). Reviewers of broadcaster/OTT apps routinely request proof of streaming rights.
- **Fix:** submit from RTSH's (or MCN's, with written RTSH authorization) **organization** developer accounts on both stores (also avoids Play's 12-testers/14-days closed-testing rule that applies to personal accounts, and satisfies D-U-N-S verification). Keep the authorization/rights documentation ready for reviewer requests. EAS `owner` can stay a personal org for builds, but store accounts must be the legal publisher.

### 8. [BOTH] Content-rating questionnaires with 18+ live content — answer deliberately
- **Evidence:** adult-flagged programmes gated by the parental PIN ([ARCHITECTURE.md → Parental control]); live broadcast content is inherently unrated.
- **Policy:** Apple's new granular age-rating questionnaire (4+/9+/13+/16+/18+, mandatory since 2026-01-31 — new apps answer at first submission; covers in-app controls and capabilities, where the parental PIN should be declared). Google IARC questionnaire similarly.
- **Fix (console):** answer for "unrestricted/live media access with parental controls"; expect a 16+/18+ rating. Misrating is an enforcement risk on both stores; a deliberately-argued rating with the PIN declared is defensible.

### 9. [GOOGLE] Data safety form — exact declarations required
- **Evidence (what the code actually collects):** email, username, birthdate, gender, city/country (registration, [ARCHITECTURE.md → Auth §6]); device identifiers (`deviceKey` keychain UUID via `PUT /users/me/device`); watch/usage analytics **currently disabled** (mounts commented out); first-party ads with `deviceClass` attribution on impressions; all traffic TLS.
- **Fix (console):** declare Personal info (email, name, DOB, gender), Approximate location (city/country — user-provided profile field, still declare), Device or other IDs, App interactions *only if* analytics ships enabled. Declare in-transit encryption ✓ and the deletion mechanism (needs item 2's URL). If analytics is re-enabled later, the form must be updated in the same release.

## Found and fixed outside the audit — unearned iOS permission strings (2026-07-29)

Not previously reported, because no prior pass inspected a **built** `Info.plist`. Two
`NS*UsageDescription` strings were being injected by config plugins for permissions the app never
requests — the class Apple's own guidance calls out (a declared reason with no feature behind it
invites a 2.1 / privacy question at review):

| String | Injected by | Reality |
|---|---|---|
| `NSFaceIDUsageDescription` | `expo-secure-store` (default) | SecureStore is used purely as a keychain wrapper (`lib/keychain.ts`); `requireAuthentication` is never set, so Face ID is never invoked |
| `NSMicrophoneUsageDescription` | `expo-audio` (default) | Radio is playback-only. `recordAudioAndroid: false` had already covered the **Android** half; the iOS string was untouched |

Fixed in `app.config.ts` with `faceIDPermission: false` / `microphonePermission: false` —
`@expo/config-plugins`' `applyPermissions` deletes the key on an explicit `false`. Confirmed absent
from `expo config --type introspect`. **Requires the next native build to land**; the currently
installed preview artifact still carries both.

Why it went unseen: these strings exist **only** in the built artifact — they never appear in
`app.config.ts`, so no amount of source scanning could surface them. Note also that
`NSLocalNetworkUsageDescription` (from `expo-dev-launcher`) *does* appear in `expo config
--type introspect` yet is **absent from the Release artifact** — introspect over-reports, so the
binary is the only trustworthy evidence for Info.plist questions.
