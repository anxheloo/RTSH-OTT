# Boot / Splash gate

## How it works today (post native-splash-only rework 2026-06-17)

The JS `BrandedSplash` was removed — boot is now native splash → router, no JS splash phase and no progress bar.

1. **Native splash** (`expo-splash-screen` config in `app.config.ts`) — shows the logo from frame zero, brand-black, and **stays up for the whole boot** (it's not hidden until React is ready). Both platforms show the lowercase "rtsh" mark (`assets/images/splash-icon.png`, 1440×943, rendered from the same SVG as the header's `RtshWordmark`) — iOS at `imageWidth: 200`, Android at `imageWidth: 160`. The "sh" is knocked out (transparent), so on the black splash it reads black inside the red disc — intended, not a missing fill. Android 12+ constrains the splash icon to a ~192dp circle: at 160dp wide (~105dp tall) every opaque pixel sits inside it, since the circle only clips the empty corners of the bounding box.
2. **Router** — `_layout.tsx` is split into **`RootLayout`** (providers only: `QueryClientProvider` → `KeyboardProvider`) and **`RootLayoutNav`** (all hooks + the `Stack`). The one-time wiring (`setupAuthRefresh`, `setupFocusManager`, `initI18n`) runs at **module scope** in `_layout.tsx` (not in render). `RootLayoutNav` calls the boot hooks directly — `useFonts`, `useCheckToken`, `useNetworkMonitor`, `useSystemTheme`, `useOTA` — and calls `SplashScreen.hideAsync()` once **all three gates resolve** (`fontsLoaded && tokenChecked && updateChecked`, the last from `useOTA` — see the OTA bullet below). `useCheckToken`'s keychain read is **async** (`expo-secure-store`), so `RootLayoutNav` **returns `null` until `fontsLoaded && tokenChecked`** (the brand-black root window / native splash holds) — the `Stack` never renders before `isAuthenticated` is known. This makes the `(auth)`/`(app)` guards key on the correct **store** `isAuthenticated` with no flash on cold boot **or JS/Metro reload** (the native splash only covers a cold launch; on a reload there is no native splash, so the `return null` gate is what prevents the login flash). Guards key on `isAuthenticated`, never the in-memory access token (null on cold boot).

Boot gates: `useCheckToken` (keychain check) + `useFonts` (Inter) + `useOTA` (published update, capped at 10s — `UPDATE_WAIT_MS`). `SplashScreen.preventAutoHideAsync()` is called at module load in `_layout.tsx`. Native rebuild required when the splash config changes (config-plugin output).

## Why these choices

- **`RootLayout` / `RootLayoutNav` split.** Every TanStack hook (`useCheckToken`, and `useMeQuery` in `(app)/_layout.tsx`) needs a `QueryClientProvider` _ancestor_. Calling them in the same component that renders the provider in its JSX would leave them with no client in scope. The split puts all hooks in `RootLayoutNav`, rendered _inside_ the providers.
- **Native splash only (2026-06-17, supersedes the 2026-06-12 three-phase `BrandedSplash` handoff).** The native logo splash already covers the entire boot window (offline-first boot is near-instant), so the JS progress bar added a phase + a handoff seam for no real benefit. Removing `BrandedSplash` deletes the only place the native→JS swap could flicker. The native splash and the `BrandHeader` both use the lowercase "rtsh" mark (rebrand 2026-09-22, replacing the stacked-squares "RTSH" lockup), so boot hands off to the first screen with no brand change.
- **Hide on fonts + keychain check.** Both essentially instant. No network blocking — `useCheckToken` is a keychain read only.
- **OTA gates the splash for at most 10 seconds, then never again (reworked 2026-09-22 — superseded "OTA does NOT gate splash").** `useOTA` applies a published update **silently**: online, it checks + downloads while the native splash is still up and, if the download lands within `UPDATE_WAIT_MS` (10000), `reloadAsync`s into it behind a brand-black reload screen, so the user only ever sees the new JS. Offline (`NetInfo`), slower than that, or any error → the current bundle boots immediately; a download already under way finishes and applies on the **next cold start**, never mid-session. There is **no "Update available" prompt any more** — it was dropped (with its `update.ota_*` strings) because a prompt most users decline leaves them on old JS, and because the store-update notice below needs updates to land without a tap. The JS calls queue behind expo-updates' own `ON_LOAD` startup check (a serial native state-machine queue, read in `EnabledAppController.swift`), so a download the native side already started is reused, not repeated. **Trade-off:** a bad update now reaches every user on their next launch with nobody able to decline it — so production updates go out with `--rollout-percentage` first and are pulled with `eas update:revert-update-rollout` (runbook: CLAUDE.md → Releasing). **The deadline exists for the hung-network case, not for download size** (a bundle is ~1-2 MB and lands in about a second): a captive portal / dead cell / unreachable origin does not fail, it hangs, and `NetInfo` still reports connected — while the only other floor is the native download timeout, **60s per request on iOS** (`FileDownloader.DefaultTimeoutInterval`) vs **10s on Android** (`max(launchWaitMs, 10_000)`), i.e. up to ~2 minutes of splash across check + fetch. **Boot and reload resolve through ONE one-shot transition** (`settle`, the only place the deadline is cleared), so the timer cannot fire after a reload is claimed and a reload cannot be claimed after boot — the alternative (a boolean read, then a reload issued) leaves a window where a download finishing on the deadline flashes the old UI before restarting. `booting` is terminal, `reloading` deliberately is NOT: a rejected `reloadAsync` reopens the gate instead of stranding the user on the splash. Locked by `hooks/__tests__/useOTA.test.ts` (7 cases: disabled, no update, reload, offline, past-deadline, reload-failure recovery, check failure).
- **Store-update notice — for what an OTA cannot ship (2026-09-22).** `constants/appUpdate.ts → STORE_UPDATE_MODE` (`'off' | 'notice' | 'block'`) tells users of **this** runtime that a newer store version exists. `'notice'` renders `StoreUpdateBanner` — a strip under `BrandHeader` that cannot be closed and opens `openStoreListing()` (the App Store / Play app, falling back to the web listing where no store app exists — iOS simulator, Android TV without Play) — and `useBrandHeaderHeight` adds `STORE_UPDATE_BANNER_HEIGHT` in the same condition, so every tab screen, radio and login already clear it with no per-screen change (device-verified on the iOS simulator: login, Home, Guide). `'block'` keeps the existing blocking `forceUpdate` modal up via `useStoreUpdateBlock` (a store subscription re-raises it if another modal takes the single slot). **The switch is only ever turned on in an OTA published to an OLDER runtime, from a worktree of the newest code already live on that runtime** (the release tag only if nothing was published to it since — for `1.0.1` the tag predates the switch entirely); `main` stays `'off'`, enforced by `constants/__tests__/appUpdate.test.ts`, because a store build made from `main` would otherwise show the notice to users already on the newest version. It stays up until the user installs the new version, whose embedded bundle carries `'off'` — no version comparison needed. **Only reaches builds that contain this code:** runtime `1.0.1` once its OTA lands, and every build from `1.0.2`. Runtime `1.0` (Android builds 16/17, iOS 1.0(1)) predates it and needs its one-off OTA from its own build commit. **It reaches an old binary at that binary's own update cadence, not the splash (learned 2026-09-29):** builds before `1.0.2` embed the old prompt hook, so the first update applies only when the user taps "Update" on the prompt or on the next cold start — only then does the silent-apply hook and the banner run. Old users see a notice over days, not on their next launch.
- **An update only helps if it is DELIVERED — the quota is invisible from here (learned 2026-09-29).** EAS Update's **Free plan allows 1,000 monthly updating users**; beyond it `u.expo.dev` answers **HTTP 429** to every device while `eas update` still publishes successfully, so a correct implementation looks broken. **Since 2026-10-06 the app reports it:** `useOTA`'s catch calls `reportOtaFailure` (`lib/monitoring.ts`) — 1% sampled, one fixed fingerprint `ota-update-failed`, level `warning` — so an outage shows up in Sentry within the hour instead of after four days. It still cannot tell a 429 from a hung network by itself (the error wording differs per platform); read the event message, then confirm with the probe below. This project hit it on **2026-09-26** (real demand that month: **3,045** unique devices, so ~2/3 of users never received the 22-09 crash-fix update). It resets on the 1st of the calendar month, and the account stayed on Free by choice, so expect the block to recur within days of each month starting. **Diagnose before suspecting the code** with a bare manifest request (`curl -sI -H "expo-platform: ios" -H "expo-runtime-version: <ver>" -H "expo-channel-name: production" -H "expo-protocol-version: 1" -H "expo-api-version: 1" -H "accept: multipart/mixed" https://u.expo.dev/<projectId>`); usage is also readable via the EAS GraphQL API with the CLI session (`account.byName(...).usageMetrics.byBillingPeriod(date, service: UPDATES)`). Consequence for design: silent-apply assumes updates reach everyone, and on a capped plan they reach whoever launches first that month.
- **Network does NOT gate splash.** Offline-first.

## Known gaps

- Font load failure is silently swallowed (`hideAsync` keys on `fontsLoaded` only, not on a font error). With no Sentry, font load failures are invisible. Tracked: **5.X.12** (Sentry init).
- ~~No error boundary at root.~~ **Resolved 2026-07-03:** `app/_layout.tsx` exports a named `ErrorBoundary` (expo-router convention) — a dependency-free branded retry screen (no store/i18n/tokens on purpose: any of those could be the crash source), dev-only error detail, `retry` re-renders the subtree.
