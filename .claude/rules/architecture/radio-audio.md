# Radio audio (cross-screen playback)

## How it works today (post 22.11)

- **Single engine above the router.** `RadioAudioHost` (`components/Media/RadioAudioHost.tsx`) is mounted once in `(app)/_layout.tsx`, wrapping the `Stack` and `RadioMiniPlayer`. It owns the only `expo-audio` player and renders no UI of its own — it wraps the router only to share that player through context (`useRadioAudioPlayer`, added 2026-09-22), so a screen can read status and seek without owning the engine.
- **Store-driven.** The host is purely reactive to `PlayerSlice`: `player.replace({uri})` when `radioStreamUrl` changes, `player.play()/pause()` when `radioIsPlaying` (or the stream) changes. It sets a background-capable audio session once (`setAudioModeAsync`), **on the first station select, not at mount**. Every engine command runs through `engine()`, which reports a throw to Sentry instead of letting it escape: expo-audio throws synchronously when the native session is in a bad state ("Session lookup failed"), and a throw inside an effect unmounted the whole app into the root error screen (REACT-NATIVE-RTSH-OTT-26, 2026-10-06).
- **Nothing touches the engine until a station is first selected (2026-09-29, REACT-NATIVE-RTSH-OTT-24).** The host mounts with the `(app)` layout, in the same moment as the profile fetch, socket and app-open ads query. On Android every sync expo-audio call (`pause`, `clearLockScreenControls`, …) blocks the JS thread on a main-thread hop (`AudioModule.runOnMain` → `runBlocking`), and the first `setAudioModeAsync` pays a one-time Kotlin-reflection init to convert its object argument — multi-second on a low-end armv7 TV box, with GC. An ANR dump caught both in the cold-start window with no radio playing. ~~An `engaged` ref gated the audio mode and the no-station `pause` / `clearLockScreenControls`.~~ **The engine itself is now lazy (2026-10-06, REACT-NATIVE-RTSH-OTT-2V).** The trace showed it mattered: building the player at mount (`useAudioPlayer(null)` → `AudioPlayer.<init>` → media3 `MediaSession` on the Android main thread) ANR'd a W2 box at `__root` for a user who never opened radio. `RadioAudioHost` now latches `engaged` on the first station select (adjust-during-render, same commit) and mounts a sibling `RadioEngine` that owns the player and every command; it is never unmounted afterwards, so closing a station still only pauses and clears. The engine is a sibling, not a wrapper, so its arrival never remounts the router. `useRadioAudioPlayer()` returns `AudioPlayer | null` (null before the first select and for the one commit the engine is created in); `RadioSeekBar` renders nothing while it is null. Locked by `components/Media/__tests__/RadioAudioHost.test.tsx` (no player constructed until a station is selected — fails on the old host; children never remount across select → close → reselect). Device-verified on `RTSH_TV_API34` (release build, demo login): radio starts from the Home list, the media session reports PLAYING. **Device-verified 2026-09-29**, with a JS hook counting every expo-audio call against the live backend: on the Android TV emulator (`RTSH_TV_API34`, demo login) and a physical iPhone 12 Pro Max (iOS 26.4, guest). Entering the app records 0 calls; first station → `setAudioModeAsync` once, then `replace` → `setActiveForLockScreen` → `play`; station switch → no second audio-mode call; close → `pause` + `clearLockScreenControls`. On iOS `play` now fires ~27 ms before the async audio mode settles, and background playback, the lock-screen widget and its play/pause all still work. **Station-switch blip — fixed 2026-09-29.** On iOS a station switch logged a spurious `pause` then `play` ~300 ms later (the TV didn't). Root cause, read in expo-audio's source: iOS `replaceCurrentSource` calls `ref.pause()` on the OLD item before swapping it (`AudioPlayer.swift`), so for an instant the engine reports loaded + not buffering + not playing — a frame `resolveExternalPlaybackChange` rightly treats as a lock-screen pause. Android's `setMediaSource` never pauses. The host now sets an `awaitingStart` ref before every `replace` and clears it on the new source's first playing frame; while it's set a paused frame carries no verdict (a lock-screen *play* still wins). Device-verified on the iPhone the same day: the switch logs `replace` → `setActiveForLockScreen` → `play` with no `pause`.
- **…but the loop is CLOSED, not one-way (fixed 2026-08-14).** The store is *intent*; the OS can move the engine without going through it. iOS's lock-screen / Control Center transport and the Android media notification are wired **natively inside expo-audio** (`MediaController.swift` → `player.ref.pause()`), so JS never hears about them. The host therefore also subscribes to `playbackStatusUpdate` and mirrors the engine back via `setRadioPlaying`. Without that mirror the intent went stale and produced a compounding bug: pausing from the lock screen left the UI showing a **pause icon over silence**, and because the intent never *changed*, the store→engine effect didn't re-run either — so the user's next in-app tap wrote the value the engine already had (a no-op) and playback took **two taps** to return. Same in reverse for lock-screen play.
  - The verdict is a pure helper, `resolveExternalPlaybackChange` (`utils/audioSync.ts`, unit-tested), because "not playing" is **ambiguous**: a live stream is also not playing while it buffers, and adopting `false` there would pause a stream that was merely stalling. A paused verdict is trusted only on a **settled** frame (`isLoaded && !isBuffering && !error`); a playing frame short-circuits the guards, since the engine cannot play by accident. Both platforms support the distinction by different means — iOS sets `isBuffering` while `waitingToPlayAtSpecifiedRate`, Android reports `playing` as the *intended* state during `STATE_BUFFERING`.
  - Intent is read with `useAppStore.getState()` inside the listener, so it subscribes once per player instead of re-attaching on every play/pause. **No feedback loop:** the write re-runs the sync effect, which then commands an engine that already agrees.
- **Routes + mini-player never touch the source or play state.** `radio/[id].tsx` selects a station via `setRadioChannel(...)`; the transport + mini-player flip `radioIsPlaying`. All audio is a downstream effect of the store. `clearRadio()` (mini-player close) pauses + tears down. The one exception is **seeking a recording**: `RadioSeekBar` reads `useAudioPlayerStatus` and calls `seekTo` on the context player directly — position is not store state (it would churn the store twice a second for one screen).
- **`RadioPlayer` is now presentational** (art + name/sub + `Equalizer` + prev/play/next) — no playback logic.

## Why these choices

- **Survives navigation.** The old inline `RadioPlayer` held the player, so leaving the screen unmounted it and stopped sound — fatal for a docked mini-player and for background radio. Hoisting the engine above the router decouples lifetime from any screen.
- **Single source of truth.** Two UIs (player route + mini-player) + future lock-screen controls all converge on `PlayerSlice`; the host is the only writer to the audio device.

## Known gaps

- **Background-while-locked + lock-screen controls wired (2026-06-26).** `RadioAudioHost` sets `shouldPlayInBackground: true` in `setAudioModeAsync` (keeps the session alive when the screen locks) and calls `player.setActiveForLockScreen(true, { title, artworkUrl })` on each station change (`clearLockScreenControls()` on teardown). Entitlements come from the `expo-audio` config plugin (`enableBackgroundPlayback: true` in `app.config.ts`) — **requires a native rebuild** to take effect. `doNotMix` interruption mode (already set) is required for the OS to bind the controls to the player.
- **Lock-screen now-playing metadata IS supported** on `expo-audio@56.0.11` via `setActiveForLockScreen` / `updateLockScreenMetadata` — the earlier "SDK 56 doesn't expose `NowPlayingInfo`" note was for an older version and is no longer true. Currently we send `title` + `artworkUrl`; `artist`/`albumTitle` (e.g. ICY in-stream song titles) are unused — `expo-audio` doesn't parse ICY metadata, so a live song title would need the server-driven radio guide or a switch to `react-native-track-player`.
- **Lock-screen NEXT / PREVIOUS station are impossible on `expo-audio` — not a wiring bug on our side (verified in native source, 2026-08-14).** `MediaController.swift` (expo-audio 57.0.3) enables exactly six remote commands — `play`, `pause`, `togglePlayPause`, `changePlaybackPosition`, `skipForward`, `skipBackward` — and `nextTrackCommand` / `previousTrackCommand` appear **nowhere** in its iOS *or* Android native code. iOS always draws those two buttons in the Now Playing widget and greys them out when the command isn't enabled, which is exactly the reported symptom (tinted, unresponsive); the buttons **cannot be hidden** either, since the OS owns that widget. The public option type confirms the ceiling — `AudioLockScreenOptions` is only `{ showSeekForward, showSeekBackward, isLiveStream }`. Android is the same shape: a bare `MediaSession.Builder(context, player)` over a single-item timeline, so no skip actions there either. `AudioPlaylist` (which *does* have `next()`/`previous()`) is **not** an escape hatch — it exposes no `setActiveForLockScreen` at all, and the remote commands still aren't wired. **Closing this needs one of:** a native fork of expo-audio (which also has to invent a native→JS event, since none exists), a switch to `react-native-track-player` (full remote-command support — the same library already named above for ICY metadata), or an upstream PR. **Not attempted; accepted as a platform-library limitation.** The App Store copy promises background playback + lock-screen controls, which play/pause + artwork deliver, so it does not overpromise.
- ~~**Live radio offered a scrub bar on the lock screen.**~~ **Fixed 2026-08-14.** `setActiveForLockScreen` was called with no `options`, and expo-audio gates the scrubber on exactly that argument (`changePlaybackPositionCommand.isEnabled = !isLiveStream`, `MediaController.swift`) — so the lock screen advertised a duration and an **enabled seek** for a stream that has neither. The host now passes `{ isLiveStream: radioProgramId == null }` — `true` for live, `false` for a catch-up recording (added 2026-09-22), which is exactly what gives a recording a working lock-screen scrubber. `showSeekForward`/`showSeekBackward` stay at their `false` default for the same reason.
- ~~**No radio-EPG source.**~~ **Resolved, with a day strip (2026-07-27).** `radio/[id].tsx` reuses the SAME per-channel EPG endpoint/hook AND day-strip mechanism as the TV channel screen (`useChannelEpgQuery`, `GET /channels/{id}/epg?date=YYYY-MM-DD`, the 7-back/today/7-forward `DayStrip` + `CatchupBanner`) — a radio station is a `Channel` with `type: 'RADIO'` in the same id-space, so no new endpoint or param was needed. ~~Browsing is read-only~~ — **superseded 2026-09-22: radio has catch-up.** The backend flags every radio programme `hasCatchup: true` and serves `GET /channels/{id}/epg/{programId}` for radio exactly as for TV (verified against the live API: guests get `LOGIN_REQUIRED`), so row states now match `channel/[id]`: TODAY's airing row is `now` (toggles live, or returns to live from a recording), every finished programme is `recorded`, only not-yet-started ones are `scheduled`. A recorded tap `fetchQuery`s the shared `channelPlaybackQueryOptions` cache entry, shows the server's `noticeMessage` in a `notify` modal on a non-`ALLOWED` decision, and otherwise calls `setRadioChannel({ …, programId })`. The recording plays through the **same** `RadioAudioHost` engine — `PlayerSlice.radioProgramId` (`null` = live) is the only new state — so it survives navigation, docks in the mini-player (titled with the programme), opens a `RECORDED` watch segment, and gets a lock-screen scrubber. Guests hit `promptSignIn()` before any fetch (`GUEST_CATCHUP_ALLOWED`); a last-tap-wins counter drops a slow decision the user has since overridden or swapped station away from; and re-entering the screen from the mini-player does not yank a recording back to live. The list auto-centers on whatever is on the engine (the recording, else the airing row).

  **Seek bar (2026-09-22).** While a recording is loaded, `radio/[id]` mounts `RadioSeekBar` (`components/Media/`) under the transport: elapsed / total + a track with the same behaviour as the TV scrubber in `PlayerControls` — tap to jump, drag to scrub, and the bar holds the release point until playback reaches it (or clears it if the seek rejects). The gesture runs on the JS thread (`runOnJS(true)`), since audio has no frame to keep in sync with. Screen readers get `accessibilityRole="adjustable"` with ±15s increment/decrement. Live radio never shows it.

  **Device-verified 2026-09-22, live backend, demo account:** Android emulator (Pixel 6 API 33) — today's and yesterday's recordings play from their start, lock-screen seek on for a recording and off for live, pause/resume keeps position, re-entering from the mini-player keeps the recording, LIVE row and next-station return to live. iOS simulator (iPhone 17 Pro, iOS 26.5) — a guest tapping a recording gets `signInRequired` while live keeps playing; as a member the seek bar shows the right duration (26:59 for a 27-min slot), tap-to-seek and drag-to-scrub both land and keep playing, and the bar disappears on return to live.

  The in-app seek bar was also run on the Android emulator the same day: tap-to-seek landed at 13:41 (the OS media session reported the same 821 s) and a drag landed at 22:41, both continuing to play. On Android the total can read a few seconds (`0:20`) for the first moment of a recording while ExoPlayer loads the playlist, then settles to the real duration.

  **Play at the end restarts (2026-09-22).** Both native engines park a finished recording AT its end, where `play()` is a no-op — so on TV the button stayed on "play" and did nothing, and on radio the store flipped to playing while the engine stayed silent (a pause icon over silence). `isAtPlaybackEnd()` (`utils/playback.ts`, 1 s tolerance, never true without a finite duration) now gates both play paths: `PlayerControls` calls `player.replay()` before `play()` for a non-live source at its end, and `RadioAudioHost` does `seekTo(0)` then `play()` when a recording's intent turns on at its end. Device-verified on iOS (radio 3-min recording, TV 12:30 news): play after the end restarts from 0:00 and actually plays.

  **No parental gate on recorded radio — by product decision (2026-09-22),** not a gap: radio has none on live either. Catch-up still needs an account (`GUEST_CATCHUP_ALLOWED`; Android is login-only anyway).

  **Known gaps (radio catch-up):** the seek bar is **not D-pad operable** on TV (a pan gesture, like the TV video scrubber).

  **Layout + virtualization (reworked 2026-07-27).** The screen is a fixed two-pane body under a **floating frosted header** (the `BrandHeader` treatment — `position: absolute` + iOS `BlurView` / Android translucent solid — rather than the flat in-flow `TabHeader` that settings/account use; the favourites action was dropped). The top pane (now-playing core) and the day strip are both **fixed**; the schedule list is the only scroller. The top pane is sized to its own content rather than a `flex: 1` half — a forced 50/50 split squeezed `RadioPlayer` into overlapping the pane below, so its internals were also given a compact pass (art 160 / smaller transport). The schedule is a **`FlashList`**, not a `.map()` in a `ScrollView`: a `ProgramRow` is expensive to mount (reanimated layout + worklet, plus a native `BlurView` on Android), and building a whole day at once made switching dates visibly janky. Virtualizing also replaced the `onLayout` offset bookkeeping with a plain `scrollToIndex` for the auto-center — nothing to measure, nothing to invalidate on a day change.

  **The same treatment was then applied to `channel/[id].tsx`** (device-verified on radio first): its mobile programme list is now a `FlashList` with `recycled` rows and `scrollToIndex` centering, and `centerOnProgram` / the row-offset refs are gone. The TV drawer list is unchanged — it was already a virtualized `FlatList`, and `ProgramRow` already disables its layout animation on TV, so it never had either symptom. `activeIndex` is now shared by both branches; only the scrolling mechanism differs.
