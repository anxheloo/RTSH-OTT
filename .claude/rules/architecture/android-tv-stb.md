# Android TV / STB

## How it works today

Android TV and operator STB run the **same codebase** as mobile, not a fork — and since **2026-07-28, the same Android artifact**: ONE APK/AAB installs and runs on phone, tablet, Android TV and STB. This supersedes the earlier two-build model (`EXPO_TV=1` selecting a separate TV prebuild).

**Why one artifact is possible at all:** `Platform.isTV` on Android is resolved at **runtime**, not build time — react-native reads `UiModeManager.getCurrentModeType() == UI_MODE_TYPE_TELEVISION` (`AndroidInfoModule.kt` → `Platform.android.js`). So the same JS bundle reports `isTV: true` on a TV and `false` on a phone with no build flag, and every `src/tv/` affordance adapts itself. The only genuinely build-time TV input is the **Android manifest**, which is now written unconditionally by **`plugins/withUniversalAndroidTV.js`** (see below). Google explicitly recommends this: *"We recommend that you have a single app that supports both mobile devices and TV devices"* ([Android TV docs](https://developer.android.com/training/tv/start/start)).

`react-native` is npm-aliased to `npm:react-native-tvos@0.86.0-2` (`package.json`) — a strict superset of mainline RN 0.86.0. The alias requires `.npmrc legacy-peer-deps=true` to stop npm ERESOLVE-ing the fork against `react-native` peers, which has the side effect of also skipping peer auto-install — so two peers are pinned **explicitly** in `package.json`: `react-native-nitro-modules` (mmkv's peer; silently missing otherwise → native build fails) and `@react-native/jest-preset` (RN's own jest preset → `npm test` fails otherwise).

`EXPO_TV` is now **inert** — nothing reads it. The `*_tv` / `*_stb` EAS profiles and `*:tv:*` npm scripts are deliberately **kept** (they still build, just identically to the mobile profiles) as reference structure for other projects. `APP_PLATFORM=androidstb` still works and is still the only way to distinguish an operator STB (`DeviceType: STB_ANDROID`) from retail Android TV — see Known gaps.

- **Single-build manifest plugin (`plugins/withUniversalAndroidTV.js`)** — always-on, Android-only, purely additive. Three edits: (1) adds the `LEANBACK_LAUNCHER` category to the **existing** MAIN intent-filter (never a second filter — two filters make some launchers render the app twice), so the phone `LAUNCHER` entry survives alongside it; (2) declares nine `<uses-feature android:required="false">` entries, which is **load-bearing, not cosmetic** — Android *infers* required features from permissions (`RECORD_AUDIO` ⇒ `android.hardware.microphone`), and one implicitly-required feature makes Google Play hide the app from every TV device; `leanback` stays `false` on purpose (true would hide it from phones); (3) copies the 320×180 banner to `res/drawable-xhdpi/tv_banner.png` and sets `android:banner`. It deliberately **never touches `android:icon`** — that attribute is global, so config-tv's `androidTVIcon` option would replace the phone adaptive icon with the flat TV drawable. Related: the `expo-audio` plugin is configured `recordAudioAndroid: false` (`app.config.ts`) — we only ever play audio, and dropping `RECORD_AUDIO` removes the implied microphone requirement at the source.
- **`@react-native-tvos/config-tv` is no longer registered** (still a devDependency for a future tvOS target). Its Android half is what `withUniversalAndroidTV` replaces; it can't be run unconditionally here because the same `EXPO_TV` flag also rewrites the **iOS** project into a tvOS target (`withTVXcodeProject` / `withTVPodfile` / `withTVInfoPlist`), which would destroy the iOS build on any `expo prebuild` or `--platform all`.

- **Focus module (`src/tv/`)** — portable, `isTV` (`Platform.isTV`)-gated, inert off-TV: `useTVFocus` (`{ focused, focusProps }`), `tvFocusHighlight(color, focused, { scale? })` (returns `undefined` off-TV/unfocused so it never clobbers a base style; `scale: false` for full-width elements — the default 1.05 pop overflows a full-bleed row past the screen edge), `TVFocusZone` (a `TVFocusGuideView` wrapper, a bare fragment off-TV) for `autoFocus`/focus-trapping a region. Wired into the shared primitives (`ReusableBtn`, `ListRow`, `ChannelCard`, `ProgramRow`, …) — see `style/tv.md` for the per-component conventions.
- ~~**D-pad-into-`ScrollView` fix** (`plugins/withAndroidTVFocusFix.js`)~~ — **DELETED 2026-07-28: it was a no-op.** The RN 0.80+ regression (react-native-tvos #1087) was real — `ReactScrollView.focusSearch()` running a custom clipped-element search that bypasses `TVFocusGuideView`, gated on the `enableCustomFocusSearchOnClippedElementsAndroid` feature flag — and the plugin force-overrode that flag to `false` in `MainApplication.onCreate()`. But **react-native-tvos 0.86 ships that flag defaulting to `false`** (verified in both `ReactNativeFeatureFlagsDefaults.kt:56` and the C++ `ReactNativeFeatureFlagsDefaults.h:90`), and neither `ReactNativeNewArchitectureFeatureFlagsDefaults` nor `ReactNativeFeatureFlagsOverrides_RNOSS_Stable_Android` (what `loadReactNative()` applies) overrides it — so the patch set the flag to the value it already had. Upstream fixed the regression by flipping the default, almost certainly at the SDK 56→57 / RN 0.86 upgrade; the plugin survived that upgrade as dead code. What actually makes the D-pad flow through the channel guide is the **single vertical `FlatList`** restructure (below), not this patch. **On every SDK upgrade, re-check that default** — if upstream flips it back to `true`, the patch must return (a reminder note sits in `app.config.ts`'s plugins array).
- **Navigation model — header menu, not bottom tabs.** The bottom tab bar is hidden on TV (`(tabs)/_layout.tsx` sets `tabBarStyle: { display: 'none' }` when `isTV`; `useTabBarHeight()` returns 0) — poor 10-foot UX. Sections switch via **`TVNavButton`** (`components/Brand/`, TV-only, rendered in `BrandHeader`'s top-right): it opens a **`Modal`** route-menu drawer listing the 4 tab routes. `Modal` (not an absolute `View`) is required because `BrandHeader` clips overflow — an absolute drawer would be cut off; `Modal` paints above the whole screen including the tab bar, and `onRequestClose` wires the remote Back button.
- **Channel screen — full-screen player + guide drawer.** On TV the player takes the whole screen; the date-strip + programme list open in a **drawer** (`TVFocusZone`-trapped, opened by a header `GuideIcon` button) instead of a side-by-side layout (a side-by-side layout was prototyped first, then superseded on user preference). The drawer body is a **single vertical `FlatList`** with the date strip as `ListHeaderComponent` — two separate scrollers (a horizontal strip + a vertical list) don't reliably hand the D-pad between them on tvOS/Android TV, one list does (and auto-scrolls the focused row into view). It opens centered on and focused on the now-airing programme (`initialScrollIndex` + `ProgramRow hasTVPreferredFocus`); Back / close / selecting a programme closes it.
- **Nested-focusable gotcha.** A focusable wrapper around focusable children traps the D-pad on the outer element (a pressable strip containing pressable buttons — `RadioMiniPlayer`; a full-screen tap overlay over control buttons — `PlayerControls`). Fixed with `focusable={!isTV}` on the outer wrapper (kept for touch on mobile).
- **Player controls auto-hide on TV (2026-10-20; device-verified on `RTSH_TV_API34`)** — superseding "controls never hide on TV". `useTVAutoHide` (`src/tv/`), called by `channel/[id].tsx`, hides the whole chrome: the screen-level back + guide buttons and everything `PlayerControls` draws (title, LIVE tag, play/pause, progress bar, options). It hides 5s after the last remote key while video plays (Media3 `PlayerView`'s model and default). Any key release shows it again and restarts the countdown. OK while hidden also pauses, as YouTube and Netflix do on TV; arrows only reveal. With focus then on play/pause, the next OK resumes. That OK lands on the tap layer, whose `onPress` is keyed on `isTV`, never `tvHidden`: the same key's release reveals the chrome, and that render can commit before the click arrives. Keyed on `tvHidden`, the click then found the touch handler and only revealed, so OK paused only some of the time. It stays up while paused (`PlayerControls → onPlayingChange`) and while the guide drawer is open. Two constraints shape it:
  1. **Hidden buttons are unmounted, not faded.** A transparent button still holds focus and still presses, so OK on a hidden pause button would pause.
  2. **Something must hold focus while hidden.** Remote keys reach JS only through the focused view's chain (`ReactRootView.dispatchKeyEvent` → `ReactAndroidHWInputDeviceHelper`), so with every button gone no key would arrive. `PlayerControls`' full-screen tap layer becomes the one focusable view (`focusable` + `hasTVPreferredFocus` while hidden; unfocusable while shown, per the nested-focusable trap above).

  The reveal fires on the key **release**: the newly mounted play/pause takes focus on every reveal after the first hide, and must not catch the same OK press. A stop-and-resume with no key in between (an ad break) comes back hidden. Off-TV the hook returns `true`, so mobile keeps `PlayerControls`' own 3s tap-to-reveal. The fullscreen button is no longer passed on TV, since the player is always full-screen there.

  **Device-verified 2026-10-20** (dev build, live backend, `adb shell input keyevent` + `adb exec-out screencap`):
  - hides about 5s after playback starts, and a key's 5s countdown holds (visible at +4.2s, gone by +5.2s);
  - OK while hidden pauses and shows the controls (frame frozen, play icon); OK again resumes, and they hide 5s later;
  - an arrow while hidden reveals;
  - paused stays up past 8s, and playing again hides it;
  - the open guide drawer holds it past 10s;
  - CH− while hidden zaps, shows the new channel's title, then hides;
  - Back while hidden leaves the screen;
  - "Stream unavailable" keeps back + guide visible.

  The phone path was not device-checked: it is inert by construction (`tvHidden` never set, `onPlayingChange` not passed) and locked by `tv/__tests__/useTVAutoHide.test.ts`. **Measure this on the emulator with `adb exec-out screencap`, not argent's `screenshot`** — on this AVD argent returned frames several seconds stale (a channel screen after the app was already back on Home), which looked like a zap card stuck over the video.
- ~~**Native rebuild required to toggle TV**~~ — **gone with the single build (2026-07-28).** There is no mobile-vs-TV native dir any more: every Android prebuild produces the same TV-capable project, so `npm run prebuild:dev` / `:preview` / `:prod` are the only ones that matter and there's nothing to toggle back. (Emulator note that still applies: `expo run:android` auto-targets the single booted device — don't pass `--device <serial>`, expo matches AVD *names*, not adb serials. A TV emulator AVD defaults `hw.keyboard=no`; set it `yes` in the AVD `config.ini` + cold-restart to type with the host keyboard.)

## Why these choices

- **npm alias over a fork/separate app.** `react-native-tvos` is built as a drop-in superset specifically so a single codebase can ship both platforms; forking would double the maintenance surface for a large-screen pass that's explicitly scoped as a display-adjustment layer (22.18), not a separate product.
- **One artifact, because the only real delta is the manifest.** The two-build model existed to keep a mobile build free of leanback/focus native code. But the focus half turned out to be dead code (above), and the manifest half is purely **additive** — a `LEANBACK_LAUNCHER` category phones ignore, `uses-feature` entries that can only *widen* device compatibility, and a `banner` attribute phones don't read. Once the delta is provably additive, two artifacts buy nothing and cost double: two builds, two versionCodes, two store uploads, two things to keep in sync for 48 months. Google's own guidance says the same.
- **Runtime `isTV`, not a build flag, is the real gate.** Everything that must *behave* differently on TV already keys on `Platform.isTV`, which Android resolves from `UiModeManager` at runtime. That's strictly more robust than a prebuild flag: it can't be set wrong, can't drift between the JS and native halves, and needs no second CI path.
- **Never override a native feature flag without reading its shipped default.** The retired focus-fix patch is the cautionary tale — it forced a flag to a value upstream had already made the default, and survived an SDK upgrade as invisible dead code. Read the flag in `node_modules/react-native/.../ReactNativeFeatureFlagsDefaults.{kt,h}` before adding *or keeping* such a patch.
- **Drawer over side-by-side on the channel screen.** A side-by-side (video + guide) landscape layout is the standard OTT pattern and was built first, but the user preferred keeping the player full-screen with the guide as an on-demand overlay — simpler focus model (one drawer to trap, not two independent focus zones) at the cost of not showing the guide and video simultaneously.

## Known gaps

- ~~**Every global confirmation modal was unusable on TV**~~ — **FIXED 2026-08-17, device-verified.** `ModalWrapper`'s backdrop + sheet are two nested `TouchableOpacity` wrappers around the buttons; on TV they were focusable ancestors, so the D-pad was trapped on the wrapper and **no button could be focused at all** — logout, delete-account, `apiError` retry, `noInternet` and the blocking `forceUpdate` CTA were all visible but unpressable in every direction, with Back the only escape (and Back is deliberately disabled on `forceUpdate`, so a 426 on TV would have been an unrecoverable app). This is the *same* trap `style/tv.md → "Nested focusables trap the D-pad"` already documented and that `RadioMiniPlayer` / `PlayerControls` were already fixed for — `ModalWrapper` was simply missed. Fix is two parts, and **the first alone is insufficient**: `focusable={isTV ? false : undefined}` on both wrappers, **plus** `hasTVPreferredFocus={isTV ? true : undefined}` on the primary button, because an RN `<Modal>` is its own window and with the wrappers unfocused nothing inside it is focused at all. **Write the guard as `isTV ? false : undefined`, never `!isTV`** — `TouchableOpacity` defaults `focusable` to false when it has no `onPress`, so the `!isTV` form *adds* Android focusability off-TV; the two earlier call sites both have an `onPress`, which is why the older form never showed the defect.

- ~~**Registration was impossible on Android TV**~~ — **FIXED 2026-08-17, device-verified.** D-pad focus dead-ended at the "Edukimi" field: `describe` reported it as the **last focusable in the tree**, and 13 `down` presses plus `right` left the screen byte-identical, stranding the terms checkbox and the submit button. Root cause is **not** clipping or the `enableCustomFocusSearchOnClippedElementsAndroid` flag (that defaults `false` in both the Kotlin and C++ sources on this RN, confirming plan 22.18-TV.b's "dead code" claim) — it is `SelectInput`, the **one** component in the app built on `@expo/ui` (`Host` + `Picker`), i.e. a native **Jetpack Compose** island embedded in the RN tree. Compose owns its own focus system and does not hand the D-pad back. **This was pre-registered as a risk** in plan 22.18-TV ("`@expo/ui` Picker D-pad focus on Android Compose") and had simply never been exercised. Fix: `SelectInput` renders `SegmentedChoice` when `isTV` and keeps the native menu off-TV — education has exactly 3 options and the same form already uses that control one field above for gender. Two paired gaps surfaced on the same path and were fixed with it: `SegmentedChoice` and `Checkbox` had **no focus ring at all**, so on TV they were navigable but invisible (both now use `tvFocusHighlight(colors.focus, focused, { scale: false })`; `SegmentedChoice` needed its option extracted into a `Segment` sub-component so each can hold its own `useTVFocus`). `Checkbox` mattered because accepting the terms is *required* to register.
  **Standing rule this establishes:** a native-interop island (`@expo/ui`, any Compose/SwiftUI view) on a TV-reachable screen needs an `isTV` branch built from plain RN. It is invisible on touch and `@expo/ui` does not claim TV support.

- ~~**Home grid cards went blank after losing D-pad focus**~~ — **FIXED 2026-10-20, device-verified.** Each card focus moved off stopped drawing everything inside it (thumbnail, logo, LIVE chip, name), so the blanks piled up as you moved across the grid. They came back only on scroll or refocus. The same bug is behind the old "blank cells after returning from a channel" note. Reproduced on `RTSH_TV_API34` in the 1.0.2 preview release build and in the dev build. **Cause: `overflow: 'hidden'` on the focusable view itself** (`ChannelCard`'s `TouchableOpacity`). Found by elimination with live patches over the debugger, one change at a time. Each of these left it broken: removing `zIndex`, removing the whole focus ring, turning off TouchableOpacity's TV focus fade, cutting focus events off from JS (no re-render and no prop change at all), and disabling HWUI partial redraw (`debug.hwui.use_buffer_age false`). Removing `overflow` alone fixed it. So it is native-only: Android moving focus off a react-native-tvos 0.86 view that clips its own children (`ReactViewGroup.dispatchDraw → clipToPaddingBox`). The blank cards' native properties (alpha, scale, visibility, bounds; read with `cmd window dump-visible-window-views`) matched the cards that still drew. The exact native line was not found. **Fix:** the touchable keeps `borderRadius` and the focus ring; an inner `View` that never takes focus does the `overflow: 'hidden'` clip. `HeroCarousel` had the same pattern and got the same fix (it is commented out today). Every other TV row (`StationRow`, `GuideRow`, `SearchResultRow`, `RadioMiniPlayer`) already clips in an inner view. Verified by walking 12 cards across 3 rows and opening and closing a channel: none went blank, corners stay rounded, ring visible. **Not yet seen on a real TV box.**

- **TV/tablet large-screen display-adjustment pass (22.18) is not done.** The current screens still run the **mobile portrait** layout on TV (the channel screen and — since 2026-08-06 — `radio/[id]` are the only ones with a TV branch) — on a 1920×1080 screen the portrait inline video (`width:100%` + `aspectRatio:16/9`) renders at the full screen height, so anything stacked below it (day-strip, EPG list on non-channel screens) sits below the fold with nothing to scroll it into view. Root-caused 2026-07-07 (confirmed via a UI-tree dump on a real TV emulator boot) as a **layout** gap, not a focus bug — the D-pad/focus foundation itself works (Home grid nav, focus rings all verified on-device).

  **Severity corrected 2026-08-17 — this entry overstated the remaining layout risk, and the two real blockers were focus bugs it explicitly ruled out.** A full remote walk of the production APK against the live backend (960×540dp, `mCurUiMode=0x24`) found the non-branched screens **render and scroll correctly**: Profile and Settings both reach their last row (delete-account / version) because a `ScrollView` follows D-pad focus; auth forms scroll; the `(modals)` sheets auto-focus their first option, hold focus against `up`, and dismiss on Back; Home's grid, the route menu, the channel player, the guide drawer and live HLS playback all work. The "stacked below the fold with nothing to scroll it into view" wording describes the **pre-drawer** channel screen and no longer generalizes. What *did* fail were the two focus defects above — so the "the focus foundation itself works" claim was true only for the surfaces that had been walked. **What remains genuinely unverified is overscan (TV-OV): an emulator renders 1:1 into a host window and has no overscan at all**, so a zero-margin layout looks perfect there and can still be clipped on a real panel — the player's back chevron and pause button sit ~30dp from the edges against a ~48/27dp guidance margin. Also still open: no screen sets `hasTVPreferredFocus` outside `ModalWrapper` and the channel drawer, so most screens mount with nothing focused. (Home's blank grid cells, listed here until 2026-10-20, are fixed — see the "Home grid cards went blank" entry above.)

- ~~**`radio/[id]` unusable on TV**~~ — **fixed 2026-08-06** (device-verified on `RTSH_TV_API34`). Two independent defects, stacked:

  1. **`RadioPlayer`'s artwork was never square** — `styles.art` was `width: '48%'` + `maxWidth: 160` + `aspectRatio: 1`, and **Yoga derives the aspect-ratio height from the PERCENTAGE-resolved width, then clamps only the width to `maxWidth`.** So on any parent wider than `160 / 0.48 ≈ 334dp` the box rendered 160 wide by (48% of parent) tall. On TV that parent is the 820dp `useContentWidth('player')` column ⇒ **160×394** — 73% of the TV's 540dp height, one box. Everything under it (equalizer, transport, day strip, the whole EPG list) fell below the fold of a screen that deliberately does not scroll. Fixed by clamping **both** axes (`maxHeight: ART`); below 334dp neither clamp binds and the 48% square is unchanged. **This was NOT TV-only** — phone rendered 160×189 and tablet likewise; both were quietly non-square since the component was written, just not fatal there. Proven on device by hit-testing the live tree (`x=390,y=281` outside the art, `x=405,y=440` inside it), not inferred from pixels.

     **This is the SAME trap already diagnosed on `channel/[id]` on 2026-07-28** — see its `videoBoxStyle` comment: *"`maxWidth` and `aspectRatio` on the SAME node is what made this box 820dp wide but far taller than 820×9/16 — the aspect height is derived before the clamp."* It was fixed there **locally** (the `videoSplit` style unsets `maxWidth`) and never generalized, so the same construct sat unnoticed in `RadioPlayer` — and in a **second copy**, `radio/[id]`'s `styles.skeletonArt`, which was missed on the first pass of this fix and caught on review. The skeleton copy was the worse of the two: `skeletonBody` carries no `contentWidth`, so its parent is the full 960dp window ⇒ 461dp of tower. Now recorded as a rule in `style/screens-and-lists.md → Things worth avoiding` so the next occurrence is caught at write time.

     **Latent instance still open:** `channel/[id]`'s `styles.video` (`width: '100%'` + `aspectRatio: 16/9`) takes its `maxWidth` from `contentWidth` (820). The 2026-07-28 note reasons the clamp "never binds in portrait" from an **800dp** test tablet — but that is a property of that device, not of portrait. iPad Pro 11" portrait is **834dp** (binds by 14dp, ~8dp too tall — small enough to pass the 2026-07-29 device check unnoticed) and iPad Pro 13" portrait is **1024dp** (height derived from 1024 instead of 820 ⇒ the player renders ~115dp too tall). Not reproduced yet — needs an iPad Pro 13" / large-tablet portrait pass.
  2. **TV was excluded from the split layout** — `splitLayout` was `deviceClass === 'tablet' && isLandscape`, a deliberate 22.18 deferral. But a 1080p set at density 320 is **540dp tall — SHORTER than the phone the stacked layout was drawn for** — while `UI_SCALE` steps every token up 1.3×. Even with the art square, the schedule got ~43dp, under one row. TV now takes the same split as tablet landscape (`deviceClass === 'tv' || (tablet && landscape)`), with no `isLandscape` test for TV since a TV is always landscape.

  **The cross-scroller D-pad hand-off that `→ Android TV / STB` warns about did NOT materialize here** — verified by walking the remote, not assumed: focus flows list → day strip at the top of the list, strip → header back button off its left end, and list row → transport when the row is at matching height. The transport is reachable; the one skip observed (`play` → back, passing `prev`) is correct — `prev` is `disabled` on the first station. Left unchanged deliberately: the strip is still a horizontal `FlatList` sibling of the vertical `FlashList`, NOT folded into `ListHeaderComponent` like the channel screen's TV drawer, because folding it in would make it scroll away and break parity with the tablet design.
- **Endless animations are an ANR risk on TV — react-native-tvos does a binder IPC on EVERY View props update (found 2026-09-29, REACT-NATIVE-RTSH-OTT-1K).** `ReactViewManager.onAfterUpdateTransaction` → `manageFocusGuideAccessibilityDelegate` calls `AccessibilityManager.getEnabledAccessibilityServiceList()` — a synchronous call into `system_server` — every time any View's props change, including Reanimated's per-frame synchronous prop updates. So each continuously animated view costs one system call per frame on the main thread; the -1K dump caught the main thread parked in that binder call during a screen transition on a low-end TV box. **JS mitigation (shipped by OTA):** the app's two endless loops — `Skeleton`'s pulse and the radio `Equalizer` — are static on TV (`isTV`). Measured on `RTSH_TV_API34` with radio playing: main-thread CPU over 10 s dropped from **659 ticks (looping) to 45 (static)**, ~14×. Rule in `style/tv.md`. **Root fix is native and needs a binary:** patch react-native-tvos to cache the TalkBack state (listen for `AccessibilityStateChangeListener`) instead of querying per update — **fixed upstream, not yet released for 0.86** (see below). Finite animations (layout transitions, fades) still pay the cost per frame while they run.
  **Measured 2026-10-06, and still the biggest main-thread binder cost.** Perfetto on `RTSH_TV_API34` (release build, animations already static): ~25 s of Home → channel → back → list navigation made **167** `getEnabledAccessibilityServiceList` calls from the main thread, **140 ms** blocked in total, max **16.8 ms** per call — 63% of all main-thread binder transactions. Cold start alone makes 22. An exact, behaviour-preserving fix exists (`if (!accessibilityManager.isEnabled) → not TalkBack`, a locally cached flag — no service enabled ⇒ the list is empty). **But it cannot be applied from this repo:** React Native's Android code ships as a **prebuilt AAR** (`io.github.react-native-tvos:react-android` from Maven, `app/build.gradle` → `implementation("com.facebook.react:react-android")`), so a `patch-package` edit to `node_modules/.../ReactViewManager.kt` changes nothing, and `AccessibilityManager` is `final` so it can't be wrapped. Building RN from source stays rejected (hours added to every EAS build for 48 months).
  **Fixed upstream 2026-10-07 — waiting on an npm release (checked 2026-10-19).** react-native-tvos [#1159](https://github.com/react-native-tvos/react-native-tvos/pull/1159) (*"skip the accessibility service query when TalkBack cannot matter"*) merged to `main` and was cherry-picked to the `tvos-v0.86.0` branch the same day. It shipped in `0.88.0-0` (2026-10-17), which needs a newer Expo SDK. **No 0.86 release contains it yet:** the newest, `0.86.3-0` (2026-09-18), predates it, and this app is on `0.86.2-0`. When a `0.86.x` after `0.86.3-0` is published, bump the `react-native` alias to it. It is native, so it ships only in a new binary. Re-run the Perfetto count above to confirm it drops near zero. Play Console reports the same ANR with a generic SDK-provider note ("forwards the call to the system"); the fix is this one.
- **Startup ANRs that no OTA can reach (triaged 2026-09-29, on 1.0.2).** **-8** (the largest ANR group): while `ReactInstance` builds every Expo module on a background thread, `AudioModule`'s constructor creates an `OkHttpClient` (`AudioModule.kt:52`), and the main thread's vsync callback blocks on ART's class-loading lock (`FindClass` → `WaitHoldingLocks`) — native module init before any JS runs, 1 GB armv7 boxes. **-23**: main thread reading the resource table while creating a text view on a low-end box. **-22**: a Background ANR on a Dell x86_64 PC running an Android-12 build with video playing, main thread merely laying out text — environment, not app. None has an app-side JS lever; -8 would need an expo-audio change (lazy HTTP client) in a native build.
  **Corrected 2026-10-06 — read the main thread of these dumps carefully.** In -8 and -K the main thread sits in `JNI CallObjectMethod → ConditionVariable::WaitHoldingLocks`, and in several -8 events the JS thread is parked in the SAME frame under unrelated calls (`NewStringUTF`, `DeleteLocalRef`). That is ART suspending every thread at once (the ANR dump's own suspend-all, or a GC) — **not** a lock held by app code, so "find the lock owner" is the wrong question. What the busy threads share is that `ReactInstance` is still initialising (view-manager `@ReactProp` reflection in `createConstants`, Expo creating every view manager eagerly, kotlin-reflect record conversion, `expo-asset` hashing a font): the app is simply too slow to start on these boxes. The `AudioModule` `OkHttpClient` theory above is **rejected by measurement** — registering that module costs 1.1–4 ms in a startup trace, ~1% of RN init. - **STB is the one thing the single build can't resolve.** An operator STB and a retail Android TV box are **runtime-identical** — nothing distinguishes them — so `DeviceType: STB_ANDROID` still depends on the build-time `APP_PLATFORM=androidstb` flag (`extra.devicePlatform` → `buildTimePlatform` in `utils/device.ts`). That means a *fully* single artifact reports every STB as `ANDROID_TV`. **Proposed fix (needs backend sign-off): let the backend classify it.** The login/register-verify `device` object already carries `model`, and the backend already bakes `dc` into the access token — so the client can send `ANDROID_TV` + the model string and the server maps known operator models → `STB`. A new box SKU then becomes a backend config row instead of an app release, which matters over a 48-month contract. Loose end: `getDeviceClass()` is still read client-side for the ad-impression beacon's `?deviceClass=` param, which would report `TV` for STBs until the backend corrects it on its side. Until that lands, the `*_stb` EAS profiles remain the escape hatch.
- **Play Store TV filtering is unverifiable off-store.** Sideloading (`adb install`) bypasses Play's feature filtering entirely, so the `uses-feature` / `RECORD_AUDIO` work can only be proven by `aapt2 dump badging` output plus Play Console's supported-device count after upload — never by a device test. Adding the leanback intent does **not** auto-publish to TV either: the TV form factor still needs an explicit Play Console opt-in with TV screenshots + a 1280×720 banner and a TV review.
- **STB self-update flow not built** — the `GET /app/version?platform=` endpoint exists (sideload poll) but the boot check/download/install orchestration lands with the rest of the TV pass.
